## From the 10 September round

- **coder is now blocked, not merely watched, when it is not in a worktree.** `enforce-agent-scope.sh` refuses any writing git command whose target directory git cannot show to be a linked worktree, including a directory that is not a repository at all. This is the only preventive check in the fleet and it enforces coder's own second step. The cost is real and worth stating: if isolation does not hold, coder stops rather than leaking commits into whatever checkout it is in. If it starts raising blockers about worktrees, that hook is why, and the fix is isolation rather than the check. See hooks/README.md item 18.
- **Worktree isolation for a workflow-spawned coder has still never been observed.** In the probe both agents ran in the main checkout and raced each other for the same HEAD. That is explained - the probe repo had no remote, `worktree.baseRef` defaults to `fresh`, and `git worktree add <path> origin/main` fails outright with no origin - but explained is not the same as disproved. It is why `fix: true` is opt-in, why the fix prompt tells coder to `git switch -c fix/<round> <reviewed sha>` rather than trusting the base it was given, and why a fix found only in the main checkout stops the run instead of being adopted. One live run in a repo with a remote settles it.
- **`fix: true` has never been run against a live Claude.** Every branch of it is covered by deterministic tests that stub the model out, which is exactly the coverage that hid the gate bug for a fortnight. What those cannot prove: that the git lanes report `isMain` correctly off `git worktree list --porcelain`, that coder follows the `git switch` instruction, and that `parallel()` returns lanes in a shape the tests-lane lookup finds. The lookup is by name rather than by position for that reason.
- **The gate's accepted gap.** `board-subagent-stop.sh` now passes any run whose final message is absent. The probe proved a schema spawn produces that; it did not prove the converse, so a fleet run that ends without a final message for some other reason - interrupted, out of context, ended on a tool call - now exits 0 silently where it used to exit 2. That is a deliberate trade against deadlocking every workflow in the fleet, and item 16 names it as a gap rather than a diagnosis. Reading `agent_transcript_path` for a StructuredOutput `tool_use` block is what would turn the discriminator into evidence.
- **`agentType`-less lanes are governed by nothing.** The SubagentStop matcher skips them and every branch of enforce-agent-scope.sh keys on an agent name, so "read-only git only" in a lane prompt is an instruction to a model, not a boundary. The four mechanical lanes have always been in that position - they run the project's test suite - and review-round's two git lanes now join them. Widening scout's or reviewer's allowlist instead would have weakened a role boundary for every run rather than for the one workflow that needs `worktree`, `merge-base` and `rev-parse`.

- **`refute: true` and the refutation stage have never been run against a live Claude either.** Every branch is covered by tests that stub the model out, which is exactly the coverage that hid the handoff-gate bug for a fortnight. What those cannot prove: that a refuter asked to attack a change actually copies out of the project rather than mutating the tree under test, and that `readHandoff` on a real refutation finds the `Blocker:` lines the way the fixtures say it will.
- **Worktree isolation for a workflow-spawned coder still has not been observed.** Unchanged from the last round, and now load-bearing in a second place: `enforce_coder` refuses a writing git command outside a linked worktree, so if isolation does not hold, coder stops rather than committing to a shared checkout. That is the intended failure, but `review-round` can now also chain a refutation onto a fix under `fix: true`, so loop work built on this round's additions may not run at all until the underlying question is settled.
- **Nothing checks that a refutation contains mutation evidence, and a refuter that reviews instead therefore reads as clean.** `review-round` stops on a `Blocker:` line and on an empty refutation, and treats everything else as unbroken. It never looks at whether the Done section says anything was mutated. Confirmed by running the workflow: a refutation whose only Done bullet is "I read the diff and it looks fine to me" returns `stopped: "clean"` and `approved: true`, which is the exact failure the role exists to prevent, arriving through the gate rather than around it. Spec section 9's "Mutation evidence present | the workflow" row assigns this to the workflow and no task built it. The plan deferred it on purpose, and the reason is good: the check would have to pin a workflow decision to coder's Done-bullet wording invented on the same day, and a format obligation invented and depended on in one commit is how format obligations decay. What is not good is that the plan promised this entry at Task 11 Step 4 and nobody wrote it, so a deliberate deferral has been sitting here indistinguishable from an oversight. It gets built once there is a real refutation handoff to parse, which needs the live run the two items above are waiting on.
- **The mutation budget per round is unbounded.** The design flagged it and nothing implements it. A refuter on a large repository runs the suite once per mutation, and nothing caps how many it tries or reports what it dropped.
- **Five ways past the scope hook, four of them open and one of them partly closed.** They belong together because they share a cause: the hook reads shell text, and a shell does not.
  - `strip_quoted` pairs quotes naively, and the general command-segmentation path that every `enforce_*` function walks still uses it unchanged: `echo "say \"x" ; git commit -m x ; echo "the end"` is allowed for `scout`, verified against this hook, even though a real shell runs the commit as its own command. The escaped quote inside the first span shifts the parity, and the later quoted `"the end"` gives the naive pairing something to close against, erasing everything between - including the commit. This round's escape-aware fix only reaches the narrower interpreter-payload regex; the general segmenter was not touched. Pre-existing, and now confirmed against the hook as it stands after this round's other fixes, not despite them - `echo "..." ; git commit -m x ; echo "end"` no longer reproduces it, because stripping the trailing inert `"end"` quotes as an ordinary word happens to restore correct parity by accident. The bug is the same one; the example that shows it had to move.
  - The 8192-byte scan bound truncates, so a verb pushed past it is never seen: `echo <9000 bytes> ; git commit -m x` is allowed, confirmed against the hook, with only a log line naming how far over the bound the command was. Deliberate, and the alternative was worse - before the bound, a long enough command blew the hook's 10-second timeout, which renders no decision at all and takes every role's guard down silently with no log. A narrow logged bypass replaced an absolute silent one.
  - The 16-segment bound truncates the same way, and it is the tighter of the two: `echo a ; ` sixteen times in front of `git commit -m x` is allowed for `refuter`, confirmed against the hook, with a log line saying how many segments were dropped. Sixteen is generous against real work - the claudecode-agents repo's whole scope-hook corpus tops out at four segments - and it exists because bytes were never the cost: 200 chained `git log` steps is 2000 bytes, a quarter of the byte bound, and measured 13.8s against a 10 second timeout before the segment bound. Same trade as the line above, a narrow logged bypass instead of an absolute silent one.
  - Segment count is bounded and per-segment word count is not, so one segment can still blow the timeout: `A=1 ` five hundred times in front of `git log` is 2007 bytes, one segment, and measures 17.2s. `command_words` spawns two processes per leading assignment or wrapper word and nothing caps how many it walks. Not closed this round because the fix is either a third bound or the single-pass rewrite that replaces all three, and the second is too large for a fix branch.
  - Variable expansion, `eval` and heredocs are unreachable by any parser reading unexpanded text, and always will be. So is any other language's inline-code flag: `python3 -c "import os; os.system('git commit -m x')"`, `node -e` and `perl -e` are all allowed, and they are `eval` wearing a different name. The hook recovers payloads from `bash -c` and its four siblings only, which its own comment states accurately; it is this list that had not said so.
  - Shell syntax in front of the command word, PARTLY closed this round and the only entry here that moved. `leading_token` read the first word of a segment as the command name, so `{ git commit -m x; }`, `( git commit -m x )`, `! git commit -m x`, `>/tmp/out git commit -m x`, `timeout 5 git commit -m x` and the body of any if, for or while were all allowed for the four denylist roles. Those are now stripped or made transparent and are denied, verified in both directions. What is still open: command substitution, `$(git commit -m x)` and the backtick form, which is allowed for `refuter`, `coder` and `ui-designer` because only `fleet-steward`, `scout` and `reviewer` check for it - the word has no leading token to remove, so the strip cannot reach it. And `script -q /dev/null git commit -m x`, which stays open on purpose: `script` puts its typescript file between itself and the command, so listing it as a wrapper would close nothing, and `script cat` would then read as `cat` while actually creating a file called `cat` - the same asymmetry that keeps `sudo` off that list.
  - The refuter's "Never write inside the project" is not enforced against Bash at all. `check-write-scope.py` only ever sees `Write`, `Edit`, `MultiEdit` and `NotebookEdit`, so `echo mutated > claudecode-agents/agents/coder.md`, `cp /tmp/x claudecode-agents/workflows/review-round.js` and `rm -rf claudecode-agents` are every one of them allowed, confirmed against the hook. The hook comment used to claim the checker held this half and now says what it really holds. `enforce_fleet_steward` resolves and checks redirection targets for an equivalent rule, so the pattern exists in the same file, and applying it here would still only reach redirections rather than `cp` or `rm` - which is why it is a design question rather than a missing line, and why it is written down instead of half-done.
- **The transcript reader fails open when it cannot read.** `board-subagent-stop.sh` consults `agent_transcript_path` to tell a schema-spawned run from one that produced nothing, and a transcript it cannot read - missing, unreadable, oversized, unparseable - passes with a log rather than blocking. Deliberate: deadlocking a subagent is worse than a rare silent pass. Unchanged by this round; written down here because nothing had recorded it yet.
